# 质量事件流程 · S4 CAPA（纠正 + 预防 + 有效性）

> **流程位置**：S3 之后。
> **本 skill 双重身份**：① **S4 节点**（起草纠正与预防措施）；② **CAPA 有效性评估方法的宿主**（2026-09-25 由 `pharma-capa-evaluator` 迁入；源 skill 已归档至 `.archive/`）。
> **报告已含 → 标注「见报告 §6」**，本步只做复核（两分是否齐、核查计划是否量化）。
> **与趋势线的分工**：本 skill 管**单事件**的核查计划；CAPA 的**批量有效性回顾**在 `qc-defect-analysis`（靠重复率/措施类型判，不在此重复）。

## 一、两分铁律（本步核心）

| 类别 | 针对什么 | 挂什么依据 | 典型动作 |
|---|---|---|---|
| **纠正**（Correction） | **事件本身** | **事件现象**（S0 六要素 / S2b 目的段） | 复验、拦截批次、修正记录、暂停使用该电极/方法 |
| **预防**（Preventive） | **根本原因** | **根本原因**（S1 结论 / S2b §4） | 改文件、改方法、改设计、加防错、横向展开到同类项目 |

- 每条措施必须标 **(纠正) / (预防)** 并挂住对应依据；输出中必须显式归类
- **两分缺一不可**：只有纠正 = 治表（根因还在）；只有预防 = 现场未收口（已发生影响未处置）
- "每条措施都回溯到根因"**不等于**两分——纠正项本来就挂现象，不强行改写成根因镜像

## 二、铁律

1. **区分"纠正 / 纠正措施 / 预防措施"**：大量无效 CAPA 的本质是把纠正（Correction）当成纠正措施（Corrective Action）。
2. **没有根本原因就没有有效 CAPA。** 若根因为"操作失误""人员疏忽""培训不到位"，直接判定**根因不成立**，评估降级为 `blocked: root_cause_invalid`。
3. **有效性指标必须可量化且有基线。** "加强培训""提高意识""加强管理"一律判 0 分，不接受辩解。
4. **"完成"≠"有效"。** 没有核查计划的 CAPA 不允许关闭。

## 三、输入契约

| 字段 | 必填 | 类型 | 说明 | 缺失策略 |
|---|---|---|---|---|
| root_cause | ✅ | text | 经确认的根本原因陈述 | 拒绝 → blocked |
| capa_items | ✅ | object[] | 每条含：类型（纠正/预防）/描述/责任人/完成时限/交付物 | 拒绝 |
| risk_level | ✅ | enum | **Critical / Major / Minor**（来自 S3，2026-09-25 统一口径） | 追问 |
| event_description | 选填 | text | 用判断纠正项的针对性 | gap |
| scope_of_occurrence | 选填 | string | 单批次/单设备/多产品/全厂 | 默认"单点"并标注 |
| effectiveness_plan | 选填 | object | 有效性核查计划（关闭前评估时必填） | gap |

> **“缺失”与“占位”是两件事（2026-09-25 用户裁决）**：上表“缺失策略”针对**结构性缺失**（内容本身不存在 → 拒绝 / blocked）。若字段**存在但为脱敏占位符**（空着 / `xxx` / 随意填写 / `待指定`），则**不拒绝**：按“未提供”照常评分与判定，结论记入 `pending_fields` + `_meta/pending_items.md`，**不阻塞流程**（见编排器「脱敏占位符处置口径」）。

## 四、第 0 步：根因有效性闸门

先检查根本原因陈述，命中任一即 `blocked`：

| 无效根因模式 | 判定 |
|---|---|
| "人员疏忽 / 操作失误 / 责任心不强" | ❌ 归因于人，未触及体系 |
| "培训不到位" | ❌ 除非能说明"为何既有培训未能防止" |
| "员工未遵守 SOP" | ❌ 需继续追问"为何 SOP 未被遵守"（SOP 不可执行？记录设计？排产压力？） |
| 根因与事件现象之间无因果链 | ❌ 需补足"为什么"链条 |

`blocked` 输出：
```yaml
status: blocked
reason: root_cause_invalid
issues: [ { pattern: "归因于人", quote: "操作人员疏忽", question: "为何该岗位既有培训与复核未能拦截？" } ]
next_step: "使用 pharma-gmp-gap-scan 重扫体系维度后重写根因"
```

## 五、措施四要素与分层

**内容 + 责任人 + 完成时限 + 交付物**（缺交付物直接打回）

```
短期（纠正）→ 中期（预防：文件/方法修订）→ 长期（工程/系统改进）
+ 有效性核查
```

- 禁止无交付物措施："加强培训""提高意识""加强管理"
- **顺序依赖必须写明**：培训排在文件修订生效之后；核查排在措施实施之后
- **力度与等级成比例**：措施力度与 S3 的 **Critical / Major / Minor** 成比例；若影响结论很轻而措施很重（或反之），须在报告中解释或调整，否则是审计追问点
- 涉及变更控制的措施（改工艺/设备/软件/供应商）→ 显式列出"需同步启动变更控制流程"，并注明**由责任部门按《变更控制管理规程》发起变更申请**——变更控制的执行属 QMS 流程，本链只做提示与交付物标注（N1）
- **涉及供应商质量问题 → 发起投诉**（作为纠正/预防措施的一项，按 QMS 供应商投诉流程执行，交付物 = 投诉单/供应商反馈）（N8）
- **涉及“方法变更后标准适用性”的预防措施，复核范围须同时覆盖两项（2026-09-25 实测教训）**：① **限度是否仍适用**（口径是否匹配）；② **该项目是否仍应作为质控项**——后者需以“是否关键质量属性”论证（含机理链 + 下游工艺控制能力 + 产品端稳定性数据）。只查①会漏掉“整个项目本就不必要”这一更优解（实例：某内包材水分项经方法变更后，最终结论为取消该质控项而非重定限度）。

### 模糊动词自检（写了 ≠ 可验收；2026-09-25 由审核端 Pitfall 16 前置）

| 模糊（打回） | 可验收（放行） |
|---|---|
| 梳理有效期清单 | 修订清单：玻璃瓶 → 棕色蓝盖瓶 |
| 加强检验员培训 | 完成异常峰识别培训并考核 |
| 完善 SOP | 修订 SOP 增加图谱 + 干扰峰判定条款 |

**自检法**：把措施动词换成"按附件 X 执行 Y"，说不通/无法验收 → 就是模糊动词。
每条措施需齐：**具体动词 + 交付物 + 责任人（具体到人，不得只写"QC"）+ 完成时限**。

### 执行边界（2026-09-25 用户裁决）

**执行跟踪与关闭核查交 QMS 台账**：本链只输出**核查计划**（指标 / 基线 / 目标 / 时点 / 判定标准）供 QMS 台账使用；**执行跟踪、到期提醒、关闭核查、CAPA 失效重开**不在本链，由 QMS 承担。报告中写明"措施执行与关闭核查按 QMS 台账跟踪"。

**链外动作清单（报告中必须声明，避免"提了没人接"）**（2026-09-25）：

| 动作 | 归属 | 链上应写什么 |
|---|---|---|
| 措施执行跟踪 / 关闭核查 / CAPA 失效重开 | QMS 台账 | "按 QMS 台账跟踪" |
| 变更申请（改工艺/设备/软件/供应商） | QMS 变更控制（《变更控制管理规程》） | 措施中列出变更控制流程与责任部门（N1） |
| 供应商质量问题导致的投诉 | QMS 供应商投诉流程 | 列为一项措施 + 交付物（投诉单/供应商反馈）（N8） |

## 六、五维评分框架（每维 0–3）

| 维度 | 问的是什么 |
|---|---|
| **D1 针对性** | 这条措施真能消除已识别的根因吗？还是只擦掉了表面现象？ |
| **D2 系统性** | 是否横向展开到所有同类风险点？还是只修了出事的那一个点？ |
| **D3 可衡量性** | 有效性指标是否量化、有基线、有目标值、有数据获取方式？ |
| **D4 可执行性** | 有明确责任人、完成时点、资源与交付物吗？ |
| **D5 无衍生风险** | 措施本身是否引入新风险？是否应走变更控制？是否需验证/确认？ |

### 每维锚点

**D1 针对性**
- 0：措施与根因无逻辑关联（如根因="清洁方法不适用"，措施="对操作员再培训"）
- 1：缓解后果，根因仍在（如"增加复检频次"）
- 2：能消除根因，但依赖人的自觉
- 3：从体系/设计层面消除根因（改方法、改设备、改记录设计、加防错）

**D2 系统性**
- 0：只处理了出事的那一个批次/那一个人
- 1：覆盖同工序，未跨工序
- 2：覆盖同产品/同设备族，有横向展开清单
- 3：覆盖全厂同类风险点，且有横向展开的证据（清单 + 完成情况）

**D3 可衡量性**
- 0：无指标，或指标不可量化（"加强""提高""确保"）
- 1：有指标但无基线（"培训覆盖率 100%"——但不知道改前是多少）
- 2：有指标 + 基线 + 目标值
- 3：有指标 + 基线 + 目标值 + 明确的数据来源与抓取时点

**D4 可执行性**
- 0：无责任人或无时限
- 1：有人有时限，无交付物
- 2：人/时限/交付物齐备
- 3：且已排入跟踪机制（CAPA 台账 + 定期回顾节点；回顾口径见 `qc-defect-analysis`）

**D5 无衍生风险**
- 0：措施明显引入新风险且未评估（如改工艺参数但未走变更）
- 1：潜在风险未识别
- 2：已识别衍生风险并有缓解措施
- 3：已判定是否需变更控制/验证确认，并已启动相应流程

## 七、判定规则

```
必要条件（任一不满足 → 整体"无效"）：
  D1 >= 2  且  D3 >= 2  且  D4 >= 2

分级：
  全部必要条件满足 且 总分 >= 13/15        → 有效
  全部必要条件满足 且 总分 10–12           → 基本有效，需补充
  任一必要条件不满足                       → 无效，需重写
  blocked（根因闸门未过）                  → 不评分
```

> **占位符与“无效”（2026-09-25 用户裁决）**：责任人／时限若为脱敏占位符（`待指定`／`xxx`／空），**D4 照判**（人 / 时限空 → D4=1 → 触发必要条件 → 整份判“无效”）—— **尺子不放松**；但该“无效”**不作为阻塞项**，**流程继续往下推**（→ S5 → S6）。同时必须：① 输出记 `verdict: 无效` + `blocking: false` + `pending_fields: [...]`；② 逐条登记 `_meta/pending_items.md`；③ 在交付物声明数据形态。**理由**：上传数据必须脱敏，占位符是**数据形态**问题，不是 CAPA 质量问题。
> **反转提醒**：唯一不允许占位的是**交付物**——“缺交付物直接打回”不变（无交付物就是结构性缺失，无法验收）。

## 八、有效性核查计划（必配输出；关闭前必做）

对每条 CAPA 生成核查计划：

```yaml
effectiveness_check:
  capa_id: CAPA-001
  metric: <量化指标>
  baseline: <改前值>
  target: <目标值>
  data_source: <从哪个系统/记录取数>
  sample_size: <样本量及确定依据>
  check_timing: <实施后 N 个批次 / N 个月>
  check_method: <趋势分析 / 抽样复核 / 现场观察 / 指标对比>
  acceptance_criteria: <达到什么算有效>
  if_failed: <无效时的处置：重新开启 CAPA 或升级>
```

**与趋势线的分工**：本步出的是**单事件**核查计划（逐条、实时、在措施完成后按计划执行）；**批量回顾**（跨年重复率、措施类型有效性）在 `qc-defect-analysis` 做，两者不重复。

## 十、治理层

- 遇到"培训"类 CAPA，**必须**追问：该岗位是否已有培训？若有，为何既有培训未防止本次事件？
- 判定"无效"时，**必须给出可直接替换的改写文本**，不能只批评。
- **不修改原 CAPA 记录**，只产出评估意见与改写建议。
- 涉及需变更控制的措施，必须显式列出"需同步启动变更控制流程"。

## 十一、闸门与不做

- 人工闸门：CAPA 批准由质量负责人/QA 决断
- **不做**：不定级（S3）、不定根因（S2b）、不执行措施、不做批量有效性回顾（趋势线）

## 十二、已知陷阱

1. **把纠正当预防**：改表面现象、根因仍在（铁律 1 的主要靶子）
2. **只写预防不写纠正**：已发生的影响未处置
3. **措施无交付物**：审计无法验证"做了没有"
4. **有效性判定标准无基线/不可量化**
5. **培训排在文件修订之前**（顺序依赖反了）
6. **改文件未走变更控制**（D5 衍生风险）
7. **只改出事的那一个点**，未横向展开同类风险（D2）
8. **没有核查计划就关闭 CAPA**（违反“完成≠有效”）
9. **把占位符当成真实内容**：责任人写 `xxx`／`待指定`／随意填写时，**不得**据此判“已有人负责”，改写建议里也不得写“责任人为 xxx 已落实”——照判“未提供”（D4 该 1 就 1），登记待补。**判“无效”但不阻塞**（占位符是数据形态问题，见编排器「脱敏占位符处置口径」）。
