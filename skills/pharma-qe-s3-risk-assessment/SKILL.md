# 质量事件流程 · S3 风险评估（两层评估）

> **流程位置**：S2b 报告之后（或 S1 直接转入，当已查明根本原因时）。
> **本 skill 双重身份**：① **S3 节点**（串两层、对齐依据、出结论）；② **三维评估方法的宿主**（2026-09-25 由 `pharma-deviation-assessment` 迁入；源 skill 已归档至 `.archive/`）。
> **报告已含 → 标注「见报告 §5」**，本步只做复核（查是否漏了第二层）。

## 一、定位

**分级器，不自己调查**——回答 **So what**（多严重、多广、要不要升级），不是 **Why**。
但评估**必须以已确认的根本原因与事件现象为依据**（见下）。

## 二、依据铁律（先过这一关）

**两层评估都必须同时挂住两样东西**：

1. **根本原因**（S1 结论「已查明」的那条，或 S2b 报告 §4 的根因判定）
2. **质量事件现象**（S0 六要素 / S2b 目的段）

缺其一 → **结论不成立**，回补后再评。禁止脱离根因单独给影响结论。

## 三、铁律

1. **三级影响分开打分**，不允许合并成一个模糊的"严重"。产品质量 / 患者安全 / 法规符合性 是三件事。
2. **取高不取平均。** 三维中任一为 3（或命中升级项）→ 整体 **Critical**；平均会掩盖致命项。
3. **范围必须有边界逻辑。** "所有批次"不是范围，"近三批 + 该批之后的连续 5 批"才是。
4. **不知道就说不知道。** 影响无法判定时 → `status: blocked` + 列出待补数据，禁止给出"初步判断为低风险"这种安慰性结论。
5. **只做第一层是不完整的**：本 skill 的**第一层**只覆盖"事件本身的直接影响"；**第二层「根因的体系扩展影响」必须做**（横向同类风险扫描 + 历史数据回溯）。
6. **不输出行动项。** 措施与时限属 S4 与流程节点；本 skill 只输出等级/范围/依据（历史遗留的 `required_actions` 已废除）。
7. **整改力度与影响结论必须成比例。** 影响结论写得极轻、措施却极重（或反之），本身就是审计追问点——审计会问"如果影响真的那么小，为什么整改这么重"。两侧都要能自洽。

## 四、输入契约

> **原因识别的推理骨架**（数据可用性 / 时间线还原 / 预期基线 / 收敛四推 / 假设-证据矩阵 / 输出契约+强度+缺口）见 `pharma-qe-s1-initial-triage/references/analysis-method.md`（单一存放处，**引用不复制**）。本节点判「影响范围是否覆盖时间区间内全部批次」时，时间窗取自该文件 §一② 的 `01e_timeline.md`——时间线上端点即窗口起点（缺时点 → 写「无法界定」并降级，不得推定）。

| 字段 | 必填 | 类型 | 说明 | 缺失策略 |
|---|---|---|---|---|
| deviation_description | ✅ | text | 已确认的事件事实描述（现象） | 拒绝 |
| root_cause | ✅ | text | 根本原因陈述（S1 结论「已查明」或 S2b 报告 §4） | 无根因时**只做第一层**，第二层标「根因未定，待补」 |
| process_step | ✅ | string | 工序/系统/设备 | 追问 |
| affected_batch | ✅ | string | 主批号/样品 | 追问 |
| detection_time | ✅ | date | 发现时间 | 追问 |
| occurrence_time | 选填 | date | 发生时间（常未知，记为 gap） | gap |
| product_type | ✅ | enum | 无菌/非无菌/原料药/生物制品/辅料 | 追问 |
| prior_occurrence | 选填 | boolean | 是否重复发生 | 默认 false 并标注 |
| qa_initial_view | 选填 | text | QA 初步意见（作对照，不是依据） | 忽略 |
| basis_versions | 选填 | object | 本次评估所依据的 SOP / 法规 / 工艺规程**版本号** | 记为 gap 并显式提示 |

**关于 `basis_versions`**：审计必然问"你当时依据的是哪一版"。缺省时本 skill 照常运行，但在 `gaps` 中留一条提示。**不要为了消除这条提示而猜测版本号。**

## 五、适用性分支（先选路）

| 事件类型 | 走法 |
|---|---|
| 影响产品/患者/法规（物料、工艺、无菌、数据）的事件 | 完整两层评估（下五节） |
| **纯实验室原因、不影响产品**（如 OOS 复测证实为实验室错误、仪器原因、无效测试） | 三维简评：D1 写"产品未受影响（依据：未放行/未用于放行判定）"，D2/D3 按实际给分；重心移到**第二层**（该根因是否影响其他批/检项数据） |
| **仪器性能核查类事件**（核查/校准/性能确认不通过，如浊度检测仪重复性确认失败） | 三维简评同上行（D1/D2=0，D3=1 偏离 SOP 未触及注册承诺）；`product_status` 写「不适用（非产品检验）」；**第二层历史数据回溯触发与否取决于失效窗口使用记录是否取证**——使用记录未取则 `historical_data.verdict: 无法判定（挂起）`，不得默认「窗口内未使用」 |

## 六、第一层：事件本身的直接影响

### 维度 1：产品质量影响（0–3）

| 分值 | 锚点 |
|---|---|
| 0 | 发生在非关键步骤，不影响任何 CQA/CPP，产品全项检验合格 |
| 1 | 触及非关键参数偏离，CQA 未受影响，需补充检验确认 |
| 2 | 触及关键工艺参数(CPP)偏离，或可能影响某项 CQA，需追加检验/稳定性考察 |
| 3 | **已确认**某项 CQA 不合格，或无菌保证受影响，或存在不可检出缺陷的风险 |

### 维度 2：患者安全影响（0–3）

| 分值 | 锚点 |
|---|---|
| 0 | 无任何暴露可能（产品未放行、未离开厂区、可被拦截） |
| 1 | 理论暴露可能，但偏差性质不产生安全性风险 |
| 2 | 产品已放行上市，偏差性质可能带来安全性风险，需医学评估 |
| 3 | 已确认或高度可能危及患者安全（无菌性、交叉污染、含量严重偏离、异物） |

### 维度 3：法规符合性影响（0–3）

| 分值 | 锚点 |
|---|---|
| 0 | 完全在注册工艺/验证范围内，无申报影响 |
| 1 | 偏离内部 SOP，但未触及注册承诺 |
| 2 | 偏离已验证状态或注册工艺描述，需评估是否触发变更申报/年报 |
| 3 | 涉及数据完整性、真实性，或需向药监报告/召回/现场检查沟通 |

### 升级项（触发即直接判「高」，不走评分）

- 涉及**数据完整性/真实性**嫌疑
- 涉及**无菌保证**
- 12 个月内**重复发生 ≥2 次**的同类事件
- 可能触发**召回**或**药监报告**
- 涉及**未经批准的变更**（实际已改变工艺/处方/供应商但未经变更控制）
- **重复发生标记强制可溯**：判「中」须写明上一次同类事件编号

### 分级规则

```
若 任一升级项命中            → Critical
否则 若 max(D1,D2,D3) == 3   → Critical
否则 若 max(D1,D2,D3) == 2   → Major
否则 若 重复发生 == true       → Major（升级一档）
否则                          → Minor

> **等级命名统一（2026-09-25 用户裁决）**：统一为 **Critical / Major / Minor**（缺陷严重度，审计语境），与缺陷线（`pharma-defect-response/references/defect-taxonomy.md`）同口径；原「高/中/低」**废止**。映射：升级项命中或任一维=3 → Critical；任一维=2 或重复发生 → Major；其余 → Minor。
```

### 波及范围界定（必须给出边界逻辑）

```
范围 = 时间窗 ∩ 物料/设备/人员关联 ∩ 工艺连续性

时间窗起点：上一次确认合格的时点（或上一次清洁验证/校准合格时点）
时间窗终点：事件被纠正并确认恢复的时点

输出必须包含：
  - included_batches: [ ]        # 明确列出
  - excluded_batches: [ ]        # ★ 同样重要：被排除的及排除理由
  - boundary_logic: <一句话说明为什么到这里为止>
  - undeterminable: [ ]          # 无法判定的批次及原因
```

**只列 included 不列 excluded 的范围界定，在审计时等于没做。**

### 影响方向性与独立验证（必须论证；2026-09-25 由审核端 Pitfall 10 前置到生成端）

**① 先定偏倚方向，再谈后果**

| 方向 | 含义 | 后果 |
|---|---|---|
| **假阳性** | 合格品被判不合格（偏高效应使真实含量合规的批次超限） | 检验资源浪费，产品质量不受影响 |
| **假阴性** | 不合格品被判合格（偏高效应使真实含量偏低的批次落入合格区） | **患者安全风险** |

- **禁令**：不得断言"偏高不会导致假阴性"——**偏高会掩盖低含量**。
- 无法排除时的正确表述：**"无法排除个别历史批次存在假阴性判定的可能性，建议在年度质量回顾中增加留样复测以最终确认"**；不得写"不会对产品质量产生不良影响"。

**② 厂家 COA 作为独立验证的前提**：厂家必须使用**不同原理**的检测方法。若厂家用相同方法与相同误差源（如同样的电极污染风险），其 COA 与我司结果一致**不能作为独立验证证据**，只能定位为"参考性数据"。

### 方法论证的来源合法性（必须核查；由审核端 Pitfall 15 前置）

凡报告引用"系统稳健性""过量设计""方法设计已考虑 XX 波动"作技术兜底，**必须先核来源并写进报告**：

| 方法来源 | 允许的表述 | 必须附的证据 |
|---|---|---|
| 药典方法 | **不得声称"设计了 X 倍过量"**（药典规定 ≠ 企业设计） | 药典通则编号 + 方法名 |
| 自建方法 | 需有验证报告支撑 | 验证报告编号 + 具体章节 |
| 内控方法 | 需有适用性评估记录 | 评估记录编号 |

审核追问四连：**来源？验证？变更控制？论证用途？**

## 七、第二层：根本原因在体系上的扩展影响

```
根因 ──┬─→ 同类风险横向扫描：还可能影响哪些产品/方法/仪器/记录/岗位？
         │    例：电极维护断点只影响某原料药？还是所有电位滴定项目？
         └─→ 历史数据回溯：该根因在历史上同样生效的批次/时间窗
               → 定量评估走 `pharma-data-integrity-assessment`

回溯不成的处理：写明「未回溯项 + 理由」，**不得默认合规**
```

| 项 | 要求 |
|---|---|
| 横向扫描 | 每个同类对象给 是/否/待核 + 依据；"待核"要写清核的方式与时点 |
| 历史数据 | 给出时间窗与批次范围；引用 `pharma-data-integrity-assessment` 的结论（数据可信/需复验/无法判定） |
| 未排查项 | 一句话说明理由（负面辩护"默认合规"禁用；用"不在质疑路径上/无历史数据，故未排查"） |

### 回溯论证的前提（关键逻辑，2026-09-25 由 `pharma-data-integrity-assessment` 补入）

> **"如果系统连抓住问题的能力都没有，那么'没发现问题'就不能作为'没有问题'的证据。"**

引用历史数据前先问：事件发生时有**当场抓住它**的手段吗——系统适用性检查？独立复核/第二方法？趋势回顾？时间窗可界定？
**没有 → 历史数据再漂亮也无法自证**，结论只能是"需复测 / 无法判定"，不能是"历史数据可靠"。定量评估走 `pharma-data-integrity-assessment`（稳健性三支柱 + 计算脚本）。

## 九、治理层

- **绝不输出"建议放行"或"建议放行与否"。** 放行是 QP/质量负责人的法定职责。
- 涉及 D3=3（数据完整性/真实性）时，输出中提示："建议上报质量负责人并按数据完整性事件启动独立调查，调查人员应独立于事发部门。"——**注：上报与组织隔离属 QMS 流程与编排节点职责，不是本评估的产出**。
- **Critical（或命中任一升级项）时的必写两项（N2，2026-09-25）**：① 上报对象与时限（质量负责人 / QA 负责人）② **启动独立调查组，调查人员独立于事发部门**；上报与组织隔离的执行归 QMS 流程，本评估只负责**点出触发**并写入输出。
- **历史数据追溯的落地动作（N7，2026-09-25）**：凡给出"建议留样复测 / 建议在年度质量回顾中增加确认"的结论，必须附一句落地归属——**由 QMS 年度质量回顾与稳定性线执行**，不是本评估完成。
- 评分与最终等级不一致（如三维都低但因升级项判高）时，必须显式解释差异原因。
- **`basis_versions` 缺失时不得推测补写**，只在 `gaps` 中提示。
- 若 `included_batches` 为空且事件确实发生 → 标记为 `blocked`，说明"范围未能界定"。

## 十、闸门与不做

- 人工确认：风险等级影响措施力度，**等级与上报由质量负责人决断**
- **不做**：不定根因（回 S2b）、不写 CAPA（S4）、不重做排查、不做调查实验、**不产行动项**

## 十一、已知陷阱

1. **只做第一层**：漏掉第二层（横向 + 历史数据），这是最常见的不完整项
2. **脱离根因给影响结论**：违反依据铁律
3. **不做历史数据回溯就下"仅本批受影响"结论**
4. **只列 included 不列 excluded**：审计时等于没做
5. **把回滚不成的项写成"默认合规"**：应写"不在质疑路径上/无历史数据，故未排查"
6. **把"未发现影响"写成"符合要求"**：两回事
7. **输出行动项与时限**（越界，已废除 `required_actions`）
8. **对纯实验室原因事件硬套完整三维**：走适用性分支，重心放第二层
